# Loader internals

This page is for contributors and for anyone debugging the framework itself. The
reverse-engineering notes (hook-point discovery, firmware signatures, HBC
structure) live in `docs/INTERNALS.md`, which is kept locally and not published.

## Runtime flow

1. **Pick the firmware's delta.** The payload embeds one bridge delta per
   supported firmware (`bridge.c`, generated table from `tools/build_deltas.js`).
   `main.c` selects the entry for `kernel_get_fw_version() >> 16`; with no entry it
   notifies `WHBridge failed: FW x.yy not supported yet` and installs nothing.
2. **Install.** `main.c` finds `SceShellUI`, attaches, and hooks the JS
   `evaluateJavaScript` entry in `libhermes`. The hook is a small detour built
   from `framework/wh_detour.h`.
3. **Rebuild the bridge.** The payload ships no Sony bytecode. The selected delta
   describes the changed hub bytecode; the detour rebuilds the bridge HBC inside
   ShellUI from the hub's own copy, after checking the hub's size and header hash
   match the dump the delta was built from. A hub that does not match runs stock.
   A delta is a list of ops: copy a run of the hub's bytes, insert literal bytes, or
   copy function headers with their bytecode and info offsets shifted. The bridge's
   new strings and longer hooked bodies move every function, so without the header
   op the whole function header table (about 350 KB) would be literal. With it, a
   delta is about 2 KB. See `tools/make_delta.js` and `tools/gen_detour.py`.
4. **Install the prelude.** The prelude runs before every evaluation. It passes
   this firmware's hub module ids (`__wh_hubmods`, see below), registers the
   payload's own `globalThis.__wh` surface and starts the loader; the bridge hands
   the hub's widget map and module `require` to it.
5. **Load widgets.** `framework/loader.js` scans `/data/wh-widgets/<id>/`, parses
   `config.json`, evaluates `widget.js` in an error boundary, and registers each
   component with the hub's widget map and Edit Widgets lists.
6. **Watch the sources.** `server.c` hashes every folder's `config.json` and
   `widget.js` at ~1 Hz (images are served live and are not hashed). A change that
   is stable for five samples triggers `wh_refresh_in_place`: the prelude is
   rebuilt, a new cave is mapped, and the hook slot is repointed - ShellUI keeps
   running. `build_prelude` stamps the prelude with `__sourceRevision`; when the
   hub evaluates its bundle again, a new revision clears the previous widget ids
   and registers the current set, while the same revision is a no-op. ShellUI
   itself is never killed for a widget change.
7. **Stay resident.** `server.c` serves widget images and the settings API on
   loopback, and watches for ShellUI respawns so a reloaded hub gets re-hooked
   without reinstalling.

## Hub runtimes

The hub's JS runtime is **kept** while you leave and come back to the hub - no
`loader ready` line appears. A new runtime is built when the shell restarts the hub
app, which is what signing out and back in does:

```
17:39:20 [hub] loader ready in the hub runtime (vendor ok, icons wrapped)
17:39:37 [hub] loader ready in the hub runtime (vendor ok, icons wrapped)   <- new runtime, no reinstall
```

The restarted runtime evaluates the cave that is already installed, so a payload
install plus a sign-out/in is enough to load a new build - no ShellUI kill, and the
`wh_kill` / `install --race` path is a recovery hatch only.

The `__sourceRevision` guard inside the prelude is for evaluations inside one
runtime (the hub bundle is evaluated more than once per load); it keeps re-running
the prelude idempotent instead of dropping widgets registered earlier.

There is no in-hub reload. The hub reached after sign-in is embedded in Home
(Hub SDK, `isStandaloneMode: false`). Launching `pshome:explorehub` opens a second,
standalone hub on top of it instead of replacing it. Calling `exitApp` on the
embedded hub leaves Home blank until the next sign-in. Home only drops and remounts
its hub after focus has stayed away from it for an unknown time. Signing out and
back in is the supported reload.

`wh_kill` / `install --race` (SIGKILL SceShellUI) is a recovery hatch for a wedged
shell, not the reload path.

## Source layout

| file | role |
|---|---|
| `main.c` | entry point: pick the firmware's delta, install, verify, report |
| `bridge.c` / `.h` | per-firmware delta table (`deltas.h` / `deltas.S` generated by `tools/build_deltas.js`) |
| `install.c` / `install.h` | cave allocation, `wh_install_once`, `wh_rehook`, `wh_refresh_in_place` |
| `hookpoint.c` / `.h` | locate the hook point from firmware signatures |
| `remote.c` / `.h` | find/attach SceShellUI, read/write memory, remote mmap |
| `prelude.c` / `.h` | build the prelude JS (config discovery, loader bootstrap) |
| `server.c` / `.h` | loopback HTTP: assets, settings, log endpoint, re-hook watcher |
| `util.c` / `.h` | version, paths, `wh.log`, notifications, byte/name helpers |
| `cave.h` | named return codes (`WH_RC_*`) shared by the installer |
| `wh_detour.h` | generated detour helper (`tools/gen_detour.py`) |
| `wh_sigs.h` | firmware signatures |
| `embed.S` | embeds `loader.min.js` into the ELF (the deltas are in the generated `deltas.S`) |
| `loader.js` | readable widget loader; minified by `tools/build_loader.js` |

## Loader surface

`loader.js` builds `globalThis.__wh`: React and the RN-PS primitives (captured
from the vendor module the hub already requires), literal enums
(`WidgetSize`, `StockTile`, `Button`), the stock-look components (`Title`,
`Label`, `TextStyles`, `Focusable`), glyph registration, the error boundary, and
the widget scheduler. Widgets see only this handle.

The bridge patches the module that builds the hub's grid `WIDGET_MAP`. It hands
the map to `__whWidgetMap` and the hub's module `require` to `__whRequire`. Every
other hub table the loader touches is a module it requires through `__whRequire`:
the stock widget frame and header, the MINI widget registry, the telemetry module,
and the Edit Widgets tables. Hub module ids move between firmware builds, so the
prelude passes this firmware's ids as `globalThis.__wh_hubmods`, keyed by the map's
module names (`stockFrame`, `stockHeader`, `miniWidgets`, `widgetTelemetry`,
`widgetIds`, `editTitles`, `editIcons`, `editDescs`, `editMenu`, `jsxRuntime`, ...).
A module the matcher could not resolve is left out:
- without the frame, the loader draws its own tile mat and settings menu;
- without the Edit Widgets tables, custom widgets cannot be added in Edit Widgets
  (`wh.log` says so);
- without the registry, MINI widgets are not shown (`wh.log` says so);
- without the telemetry module, ids are not filtered (`wh.log` says so);
- without `editMenu`, Edit Widgets shows one list with the custom widgets last;
  without `jsxRuntime`, each of the two lists counts only its own widgets toward
  the hub's minimum (`wh.log` says so).

**Stock frame.** Each tile renders inside the hub's own widget frame, with the
loader's tile as the frame's `Template`. The frame always draws the stock mat
(`#17191E` with the native light-mat effect) behind the template, so widgets draw
no background of their own. A widget's `config.json` settings become the frame's
`options` (`MenuListItemPS` rows), the menu the stock widgets use. The frame binds
Options on its own view, which never has focus (the tile view inside the template
does), so the tile calls the frame's `onOptionsKeyDown` to open it. While a tile is
entered, Options stays with the tile.

**Edit Widgets list.** The list offers the ids in the widget-id module's `EDITABLE`
table, and reads each entry's title, icon and description from three tables keyed by
widget id. They are read when the list is built, so the loader fills all four when
the hub runtime comes up (the `__whWidgetMap` setter). `wh.log`: `edit list title
set for N widget(s)` (and `iconId`, `description`).

**Stock and Custom lists.** The stock list puts custom widgets after every stock
one, so the loader splits it in two: **Stock Widgets** and **Custom Widgets**, with
L2 / R2 switching between them while the list is shown (edit modes `default` and
`modify`). A line above the list names the one shown and the L2 / R2 hint.
- The widget section reads the list component (`editMenu`, a `default` export) at
  render time and passes it the layout `config` (columns of placed ids) and the
  widget `map`. The loader replaces `default` with a wrapper that passes only the
  shown part of both, and remounts the list (`key`) when the user switches.
- The list's rows are the placed ids in `config`, then the map's other ids. It
  rebuilds them whenever `config` changes after a row got focus, so anything in
  `config` becomes a row: the wrapper can never add the other list's ids to it.
- The list lets a placed widget be turned off only when more than 3 are placed in
  the `config` it gets (`msgid_must_minimum_widgets_enabled`). That is each row's
  `enabled` prop, set when the list creates the row through the hub's jsx runtime
  (`jsxRuntime`, read at call time). With one part per list, that count would
  only include that part, so the loader wraps the runtime's `jsx`: a row that is
  placed (`active`), disabled, and in the shown list's map gets `enabled: true`
  while the whole layout has more than 3 widgets placed. Every other element passes
  through unchanged.
- L2 / R2 come from a global `KeyEventObserverPS` listener, since the list's own key
  handlers belong to the hub. They act only while the list is shown.
- `wh.log`: `edit list split into stock and custom widgets (L2 / R2)`.

**Hidden MINI widgets.** The row counts an item as shown while the ref it passed
holds an instance, and skips items without one when it lays out and scrolls the row.
`props.setVisible(false)` makes the loader hand that ref `null` and render the frame
in a transparent, absolutely positioned box, out of focus. (`overflow: 'hidden'` does
not clip on the console, so a zero-size box alone still shows the pill.) The element tree does not change, so the widget
stays mounted and can show itself again.

**Layout backup.** The saved layout is AsyncStorage `widget:customTemplates`
(`{templateId: columns of widget ids}`). A hub without the payload loads our ids as
empty cells, and its next save stores them as `null`. So the loader wraps the hub's
AsyncStorage: every write of that key is mirrored to `wh:customTemplates`, and when
the hub reads the layout (`multiGet`), the custom widgets missing from it are put
back. A save without the payload keeps a `null` where a custom widget shared a column
with stock ones and drops columns that held only custom widgets (console-verified),
so the backup's columns are lined up with the stored ones first and the dropped
columns are reinserted. Each widget then goes back into its saved cells if they are
all still empty, or else into the first free run of cells of its height. The hub sees
the restored layout before it lays out the grid. Clearing the layout clears the
backup.
`wh.log`: `layout backup on`, `layout: restored N custom widget placement(s) from the
backup`.

**Widget storage.** `props.storage` is a per-widget JSON object in the hub's
AsyncStorage (the signed-in user's database) under `wh:data:<id>`. It is loaded once
per hub runtime; writes are queued and each one stores the whole object.

**Full-screen pages.** The hub has one stack navigator (`mainNavigator`) for its
screens (`Root`, `Settings`, `Background`, ...). Its router builds the route table
once and rejects unknown names, but every caller looks its methods up per call. On the
first `openPage`, the loader wraps `getStateForAction` (a NAVIGATE to `WhPage` pushes
a route whose params name the widget), `getComponentForRouteName`,
`getComponentForState` and `getScreenOptions`. Back and the transition stay stock:
Circle pops the route by key, and at the top level Circle reaches lock A as before.
Tiles get `navigation` from the legacy context every hub screen provides
(`WidgetTile.contextTypes`). `wh.log`: `pages: route WhPage added to the main
navigator`, `page opened`, `page closed`.

**Hub state.** `props.hubVisible` comes from the `mainNavigator` router wrap (the
pages wrap above, installed on the first tile mount): the tiles are visible while
the stack's index is 0 (`Root` on top). `props.hubFocused` is `AppState` not
`inactive` / `background` (the Control Center makes it `inactive`) and, embedded,
`HubAppContext.isHubFocused` from the `hubSdk` module (false on the game row).
Console-verified on 13.20: a game stops the hub runtime (no unmount, timers
stop) and Home starts a new one on return. `wh.log`: `hub tiles covered by
<route>`, `hub tiles shown`, `hub app inactive`, `hub app active`.

**Sounds.** `wh.playSound(name)` maps a curated name to a `psfx_*` id and calls
vendor `SystemSoundPS.playByID(id)`, only when the id is in `SystemSoundPS.SoundIds`
on this firmware, at most once every 100 ms.

**Locale.** At hub start the loader requires `dateFormats` (the hub's wrapper over
the system registry), reads `getFormats()` (`{dateFormat, timeFormat}`) and
registers `registerDateTimeFormatChangeHandler` for later changes. The language is
`I18nPS.getCurrentLocale()`, read on each `wh.getLocale()`. `wh.log`: `locale: 12 h,
MM/DD/YYYY`.

**Telemetry.** At startup the hub reports the placed widget layout. Its widget
telemetry module (`widgetTelemetry`) sends an unknown id raw in
`widgetConfiguration(layout)`, and as `-1` in `widgetEncodedLayout(layout)`. Both
skip empty (`null`) cells, and their callers look them up at call time. So the
loader replaces both exports with wrappers that blank our widget ids in a copy of
the layout first. Custom ids never appear in the hub's telemetry, and the stock
widgets are reported as before. `wh.log`: `telemetry: custom widget ids filtered`.

**Telemetry switch.** Welcome Hub Settings > Telemetry: *Hide custom widgets* (the
default, the filter above) or *Off*. Every telemetry event ShellUI's JavaScript
sends goes through `NativeModules.VshNMTelemetryNq.SetEvent` (hub module 863,
`TelemetryNq`, the telemetry client's native-queue transport), and its caller looks
the method up at call time. So the loader replaces it with a gate, in every runtime
it runs in, before that runtime's app code. The setting is console-wide, kept by the
payload in `/data/wh-widgets/.hub.json` (`/__wget?w=.hub`). Until it arrives, events
wait in memory (at most 500); then they are sent, or dropped when it is *Off*. If
the payload does not answer for 30 s, events are sent as usual. A change applies at
once in the hub runtime; other runtimes read it when they next start. Native
telemetry outside ShellUI's JavaScript is not affected. `wh.log`: `telemetry: off
(N event(s) not sent so far)`.

**Welcome Hub Settings rows.** The Settings screen builds its rows in a `useMemo`
and reads each row module's `default` every time. The loader wraps the "Followed
games" row (`hubSettingsFollowedGames`, the last row always shown) so it renders
the stock row followed by *Telemetry* (a `MenuListItemPS.Dropdown`) and *Widget
Data* (a `Button` that opens the loader's own page, `WhPage` with `__wh: '.data'`;
a leading dot is never a widget id). The page lists the `wh:data:*` AsyncStorage
keys of the signed-in user and deletes them on request. `wh.log`: `settings rows
added (Telemetry, Widget data)`.

**Focus while entered.** An entered tile keeps native focus the way the stock
frame's `locked` mode does. Its arrow handlers return **false**: the RN-PS key
dispatcher resumes with `resumeEventDispatch(!result)`, so a falsy result marks the
native key event handled and the four-way focus move is skipped (a truthy result
lets the move run). The tile view also gets `cursorEndSFXEnabledDirection:
['none']`, which turns off the native "cannot move" (cursor-end) sound, and the
loader plays the move or blocked sound for its own selection. `focusCustomSettings`
`canMove*: false` stays as a fallback. `soundEffectsEnabled` does not affect focus
sounds (only Enter / Back and press sounds). When a tile's page closes, the hub does not refocus the tile; the loader
calls the tile view's `focus()` (as the hub's own overlays do) and re-enters it on
the remembered item.

**MINI widgets.** The hub's MINI ("transient") registry (`miniWidgets`) exports
`WIDGET_MAP` and `WIDGET_CONFIGS` keyed by widget id, and `WIDGET_PRIORITY`, the
order of the MINI row (stock: Transfers, Campaigns, PS Plus, Store, Highlights, New
widget). The hub root renders that row from a copy of `WIDGET_MAP` and sizes it on
its first render. So when the hub runtime comes up (the `__whWidgetMap` setter), the
loader adds each MINI widget to both maps and appends its id to `WIDGET_PRIORITY`.
MINI widgets stay out of the grid's `WIDGET_MAP` and the Edit Widgets list. The row
counts an item as shown while its callback ref holds an instance. The loader
registers a `forwardRef` wrapper and passes that ref on to the stock frame. A new
widget revision removes our ids from the registry first (`__miniReset`). `wh.log`:
`MINI row registered N widget(s) [...]`.

Widgets are hot-reloaded: `server.c` watches the drop folder, rebuilds the prelude
and swaps the hook in place, so a `config.json` / `widget.js` change lands without
restarting the payload or the shell (see the runtime flow above). The new set is
used by the next hub runtime, i.e. after signing out and back in. Changes to
`loader.js` itself still need a payload reinstall. `config.json` settings are
validated once and passed on `props.settings`.

## Asset and settings server

`server.c` listens on `127.0.0.1:8098`:

* `GET /` and `GET /<widget>/<file>` - widget images, `.png`/`.jpg`, max 1 MB,
  names validated by `wh_name_ok`.
* settings get/set endpoints used by the prelude, persisted under
  `/data/wh-widgets/<id>/.settings.json`; `w=.hub` is the loader's own
  (Welcome Hub Settings rows), `/data/wh-widgets/.hub.json`.
* `GET /__launch?uri=<url-encoded URI>` - `wh.launch`: asks ShellUI to launch the
  URI via `libSceShellUIUtil.sprx` (`sceShellUIUtilLaunchByUri`). Any URI with a
  scheme; refused if it is not fully decodable, has spaces or control characters,
  or is 512 characters or longer. 6 launches per minute, loopback only.
* `GET /__notify?text=<url-encoded UTF-8>` - `wh.notify`: a system notification
  (`sceKernelSendNotificationRequest`). At most 256 bytes after decoding; control
  characters other than newline are refused. 6 per minute, loopback only.
* `GET /__stats` - console readings for the Console Stats widget, as JSON:
  `cpuTemp` and `socTemp` in °C (`sceKernelGetCpuTemperature`,
  `sceKernelGetSocSensorTemperature(0)`), `fan` in percent
  (`sceKernelGetCurrentFanDuty(u16 *duty, u64 *chassis)`, duty out of 1024),
  `thermalAlert` 0 / 1 (`sceKernelIccIsThermalAlert`), `uptime` in seconds, and
  `storage`: one `{name, total, free}` (bytes) per mounted drive (`internal` =
  `/user`, `m2`, `extended`, `usb0`..`usb3`). A reading the console refuses is
  `null`. Memory is not reported: the FreeBSD memory sysctls do not exist for the
  payload, and Sony's own OIDs only give per-process budgets.
* the log shim that appends widget lines to `wh.log`.

## Build chain

```
node tools/build_deltas.js                 # out/deltas/: fw<NNNN>.delta + deltas.S/.h
node tools/build_loader.js                 # out/loader.min.js (terser)
python tools/gen_detour.py framework/wh_detour.h
bash framework/build.sh                    # out/wh_bridge.elf, out/wh_kill.elf, zips
```

Each `tools/fidmaps/fw<NNNN>.json` is one supported firmware. `build_deltas.js`
finds that firmware's hub dump in `dumps/` by the map's `source_sha1`, builds the
bridge with `tools/build_bridge_hbc.js`, turns it into a delta with
`tools/make_delta.js` (which verifies the rebuild byte-exact) and writes the table
the payload embeds. Hub dumps are decrypted Sony bytecode: they are never
committed or distributed (`dumps/` is git-ignored). Only the maps are.

`tools/build_bridge_hbc.js` is table-driven: each hook is one entry in `PATCHES`,
and the order of that table is part of the output format. Function ids, registers
and offsets all come from the map, because they move between firmware builds.

## Adding a firmware

1. **Dump the stock hub.** Reboot without loading `wh_bridge.elf`, open the
   Welcome Hub, then `python scripts/dump_hub.py --host <ip> --out dumps`. A
   resident wh payload swaps in its own bridge, so the script skips patched copies
   and says so.
2. **Map it.** `node tools/fid_match.js dumps/hub_fw1320_<hash>.hbc
   dumps/hub_fw<NNNN>_<hash>.hbc tools/fidmaps/fw<NNNN>.json`. The matcher finds
   the patched functions and the loader's hub modules by content, never by id.
   Exit `0` means everything resolved; `2` means unresolved entries; `3` means the
   dump is already patched. See `tools/FID_MATCH_SPEC.md` for the method and the
   per-hook operands.
3. **Build.** `node tools/build_deltas.js`, then `bash framework/build.sh`. Any
   unresolved or low-confidence entry stops the build; nothing is patched blindly.
4. **Test on that firmware's console** before releasing it.

## Verification

* `node tools/fid_match.js <13.20 dump> <13.20 dump>` (self-test) must resolve
  every target uniquely and reproduce the params in `tools/fidmaps/fw1320.json`.
* `tools/make_delta.js` applies each delta exactly like the detour does and fails
  unless the rebuilt bridge is byte-identical.
* `tools/tests/match_test.c` runs the generated detour natively against a real hub
  + bridge + delta. See `tools/tests/README.md`.
